# Общий выход YouTube и резервный вход для Yota

## Изменение для действующих подписок

Для общего российского выхода клиентский baseline продолжает отправлять YouTube
в VPN. На немецком сервере Xray выбирает российский outbound для доменов YouTube,
а остальные сервисы используют прежние маршруты. Правило применяется ко всем
пользователям существующих VLESS/Trojan-входов, без отбора UUID или отдельного
клиентского профиля. Ссылки подписок и ключи для такого серверного изменения
перевыпускать не требуется.

Российский выход — отдельный действующий узел или разрешённый прокси. Нельзя
подставить фиктивный адрес или считать немецкий VPS российским после изменения
геобазы. Отсутствие рекламы зависит от географии, которую определяет YouTube,
аккаунта и текущих правил сервиса. Маршрутизация BlancVPN на всех его серверах
остаётся неподтверждённой гипотезой.

### Подготовка конфигурации

`tools/prepare_youtube_egress.py` — самодостаточный инструмент подготовки, а не
автоматическое применение. Нужны текущий runtime Xray и **закрытый** JSON реального
VLESS/Trojan outbound с корректными учётными данными, TLS/REALITY и проверкой
сервера. Конфигурация межсерверного узла должна соответствовать установленному
Xray; проверка структуры не заменяет `Xray -test` и реального соединения.

```bash
python3 tools/prepare_youtube_egress.py \
  --xray-config /usr/local/x-ui/bin/config.json \
  --ru-outbound /root/ru-youtube-outbound.json \
  --output /root/xray-youtube-candidate.json
```

Инструмент сохраняет все inbounds, UUID, настройки DNS и старый первый outbound.
Добавляет один выход `sa-vpn-youtube-ru` и доменное правило после начальных
защитных/API-правил. Не меняет 3x-ui, службы или подписки. Кандидат создаётся
исключительно как новый файл с правами `0600`; секреты не печатаются на stdout.
Повторное применение к уже изменённому кандидату требует отдельного разбора.

Домен должен быть передан клиентом или определён серверным sniffing. Само правило
не определит YouTube по произвольному IP. До включения проверяются действующие
настройки sniffing для HTTP/TLS/QUIC и реальные запросы приложения; клиентские
direct-правила, включая тестовый `youtube-direct-test`, обходят серверное правило.
Для общего режима нужен baseline, а не профиль прямого YouTube.

Проверка синтаксиса кандидата установленным ядром:

```bash
/usr/local/x-ui/bin/xray-linux-amd64 run -test -config /root/xray-youtube-candidate.json
```

Имя бинарного файла нужно сверить с установленной версией. Успешный `-test`
проверяет конфигурацию, но не геолокацию или доступность узла.

В 3x-ui runtime `config.json` перегенерируется. До применения делается закрытая
копия БД и серверного шаблона. Из кандидата переносятся только `outbounds` и
`routing` в постоянные настройки Xray через 3x-ui; генерация входов остаётся у
панели. Затем проверяются runtime, исходные UUID/URL подписок, реальная загрузка
YouTube и остальных сервисов для нескольких действующих пользователей.
Откат восстанавливает предыдущие `outbounds`/`routing`. При недоступности выхода
автоматический fallback на другой регион этой доработкой не добавлен.

## Вход во время ограничений Yota

На [официальной странице Yota](https://www.yota.ru/whitelist) перечислены
разрешённые сервисы, включая сервисы Яндекса/VK и СКБ Контур. Это не перечень
арендных VPS или IP-диапазонов, пригодных для VPN. В
[общественном источнике наблюдений](https://github.com/hxehex/russia-mobile-internet-whitelist)
отдельно отмечается различие фильтрации Yota и МегаФона. Доступность узла у
МегаФона нельзя переносить на Yota без проверки.

Подготовка резервного входа:

1. Подобрать адрес, который встречается в наблюдениях при ограничениях именно
   Yota в нужном регионе. Общее совпадение с CIDR — только признак для отбора.
2. Подключить принадлежащий владельцу или разрешённый ему узел, проверить
   сертификат/REALITY и реальную VLESS-сессию с нужной SIM во время ограничений.
3. Добавить российский вход в **существующие** подписки как дополнительный сервер,
   сохранив нынешний немецкий вход. Изменение тела подписки выполняется после
   проверки реальной версии 3x-ui и способа её выдачи; добавление outbound на
   сервере само по себе не добавляет клиентский сервер в подписку.
4. Через российский вход YouTube выходит в РФ; остальные сервисы, требующие VPN,
   переходят на немецкий узел. Клиентские direct-исключения продолжают действовать.

При полном отсутствии мобильной передачи данных такой вход не поможет. При
фильтрации IP вместе с SNI недостаточно изменить одно имя сервера. Проверка
сертификата не отключается; список разрешённых ресурсов не заменяет доступный
вход. Применение и тестирование резервного узла ещё не выполнены.

### Один узел для двух задач, без петли

У российского узла должны быть отдельные роли: клиентский вход для Yota и
межсерверный вход для YouTube с Германии, выводящий трафик напрямую в РФ.
Транзит с РФ на немецкий сервер принимает отдельный inbound
`sa-vpn-ru-transit`. Подготовщик исключает его из правила YouTube: трафик,
пришедший через этот вход, не отправляется обратно в РФ. Другие межсерверные
входы нужно явно указать через `--exclude-inbound TAG`.

Это разделение предотвращает цикл РФ → Германия → РФ. Российский выход для
YouTube и доступность российского входа у Yota проверяются независимо.

## Проверки в репозитории

Unit-тесты проверяют сохранение ключей и защитного порядка правил, исключение
транзитного входа, отказ от непроверенного TLS и закрытые файлы кандидатов.
Интеграционный тест запускает локальные узлы Xray с проверяемым TLS и проверяет,
что YouTube у двух существующих пользователей приходит на отдельный выход,
остальные домены остаются на основном, а транзит не возвращается назад.
Локальная схема не измеряет реальную геолокацию, рекламу или фильтрацию Yota.

Первичный источник по серверным правилам:
[Xray routing](https://xtls.github.io/en/config/routing.html).
