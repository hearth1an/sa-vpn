# Маршрутизация, AnyDesk и контролируемые эксперименты

Изучено 6 октября 2026 года. Это описание реализованной конфигурации и будущих
тестов, а не отчёт об ускорении Instagram или отключении рекламы на рабочем VPS.
Ключи, IP сервера, протокол и мониторинг этой доработкой не заменяются.

## Что включено по умолчанию

Единственный источник правил — `routing.py`. Сборщик встраивает его в
`install.sh` и `tools/apply_happ_routing_3xui.py`, сохраняя запуск одним файлом.

Профиль `baseline` сохраняет имя `SA VPN - RU direct`, GlobalProxy=true,
Cloudflare DoH для proxy и Yandex DoH для direct. Порядок групп:
**block → proxy → direct → proxy по умолчанию**.

- Домены Контура (`kontur.ru`, `e-kontur.ru`, `testkontur.ru`, `skbkontur.ru`),
  включая Эльбу, а также Ozon/Wildberries и `anydesk.com`: напрямую.
- Явные домены Instagram/Meta и YouTube: через VPN, прежде широких geoip:ru.
  Добавлены вспомогательные `ig.me`, `igcdn.com`, `igsonar.com`; это полнота
  правил, не обещание ускорения — неизвестные зарубежные домены и так proxy.
- Остальные .ru/.su/.рф, российские и локальные IP: напрямую.
- Общие блокировки рекламы и приложений не включаются.

Happ использует групповые приоритеты, а не произвольное чередование исключений.
Поэтому нельзя без проверки добавить большую proxy-категорию, содержащую
домен прямого исключения: она перехватит его раньше direct. Для более сложной
иерархии нужна отдельная полная конфигурация клиента и проверка совместимости.
При обновлении Happ дождитесь загрузки геобаз и переподключитесь.

## AnyDesk: домен не равен приложению

`domain:anydesk.com` включает `*.net.anydesk.com`. Официальная документация
AnyDesk указывает TCP 80/443/6568; UDP 50001–50003 и multicast 239.255.102.18
относятся к обнаружению устройств в LAN, а не ко всему удалённому трафику.
Не направляйте весь порт 443 напрямую и не открывайте эти порты на VPN-сервере.

Для прямых подключений к IP другого компьютера требуется исключить само
приложение на устройстве. Сервер не может вернуть уже полученный туннельный
трафик в домашнее подключение клиента.

### Windows/Linux/macOS с подходящим sing-box TUN-клиентом

Получить фрагмент, ничего не меняя:

```bash
python3 tools/export_client_profiles.py --format singbox-anydesk
```

Это **не полный профиль Happ** и не готовый VPN-конфиг. В поддерживаемом клиенте
поместите правило перед общими proxy-правилами, включите распознавание процессов
и проверьте наличие outbound `direct`. Поддержку process rules в конкретной
версии Happ/Desktop нужно проверить отдельно. Установленная служба и portable/
custom AnyDesk могут иметь другие имена: сверяйте процессы фактического сеанса.
На macOS процессные правила относятся к нативному desktop-клиенту, не к iOS/
Mac Catalyst. После настройки проверьте и relay-, и прямой сеанс.

### Android/Happ

Предпочтительный вариант для обычного пользователя — вручную исключить AnyDesk
в настройках выбранных приложений Happ. Обычный пакет:
`com.anydesk.anydeskandroid`; дополнительные плагины/custom client проверьте отдельно.

Для провайдера с **уже зарегистрированным** Happ Provider ID доступен экспорт:

```bash
python3 tools/export_client_profiles.py --format happ-android-anydesk --provider-id YOUR_REGISTERED_ID
```

Вывод содержит HTTP-заголовки `providerid`, `per-app-proxy-mode: bypass` и список
AnyDesk. Их добавление в подписку не автоматизировано и по умолчанию отключено.
Не заменяйте ими настройки других платформ/существующие исключения без проверки.
Provider ID включает передачу в Happ данных устройства (HWID, ОС и хеш домена);
для домашнего использования это не обязательно — используйте ручное исключение.

### iPhone

Не обещаем произвольный process/app bypass через обычную подписку. Apple's
per-app VPN требует MDM и управляемых приложений. Для личного iPhone остаются
доменные правила и проверенные точечные IP-исключения. Полное исключение AnyDesk
одним серверным переключателем этой доработкой не реализовано.

Исключённые соединения идут через локального провайдера и видят обычный IP,
а не выходной IP VPN. Это намеренный компромисс приватности.

## Белые списки

Практический аудит текущего адреса и подготовленные опыты описаны в
[белых списках и контрольном тесте YouTube](whitelist-and-youtube-experiments.md).

Различайте direct-список клиента и разрешённые адреса мобильного оператора.
Наше правило не заставляет оператора пропустить недоступный VPN-вход.

- [hxehex/russia-mobile-internet-whitelist](https://github.com/hxehex/russia-mobile-internet-whitelist)
  собирает наблюдения о доступных доменах/IP/CIDR. Это не официальный универсальный
  API операторов: результаты зависят от оператора, региона и конкретного режима ограничений.
- [runetfreedom/russia-v2ray-rules-dat](https://github.com/runetfreedom/russia-v2ray-rules-dat)
  собирает GeoIP/GeoSite, включая ru-whitelist из предыдущего проекта и категории сервисов.

Профиль `runetfreedom` использует другой источник геобаз, категории `meta`,
`youtube` и `ru-available-only-inside`. Он имеет отдельное имя и **не включён
по умолчанию**. Для предварительного просмотра:

```bash
python3 tools/export_client_profiles.py --profile runetfreedom
python3 tools/export_client_profiles.py --profile runetfreedom --format happ-link
```

Экспорт ссылки использует `happ://routing/add/`, а не принудительный `onadd`.
Сохраняйте активным baseline; после ручного выбора эксперимента переподключитесь.
Сам экспорт не изменяет сервер/клиент. На iOS включите оптимизированные геофайлы
(Use Chunk Files) в поддерживаемой версии Happ и проверьте расход памяти.

`geoip:ru-whitelist` не добавляется в direct: общий разрешённый CIDR не означает,
что каждый адрес/порт в нём доступен, а широкий direct может выпускать трафик
из VPN. `ru-blocked`/`ru-blocked-all` не включаются автоматически из-за приоритетов
прямых исключений и размера баз. Источники latest обновляются их владельцами;
это внешний изменяемый компонент, не гарантия полноты и доступности.

Возможный отдельный эксперимент: собственный реально доступный российский вход
→ собственный зарубежный выход. Нужны доступ к обоим узлам, стоимость/нагрузка,
проверка TLS и реальной передачи через туннель у нужного оператора.
Смена SNI на произвольный чужой домен или открытый TCP-порт не доказывают обход.
Второй VPS не создан, адреса чужих серверов/ключи в репозиторий не добавляются.

## Instagram: сначала исходные замеры

Выполнить на сервере локальную диагностику без сетевых запросов и изменений:

```bash
python3 tools/network_diagnostics.py --xray-config /usr/local/x-ui/bin/config.json
# Для standalone вместо этого укажите /etc/sa-vpn/xray.json
```

Вывод содержит текущий TCP congestion control, доступные алгоритмы, default
qdisc, MTU интерфейсов и только разрешённые поля транспорта. UUID/пароли/
подписки/полный конфиг не выводятся. Отсутствующие данные отмечаются явно.
Default qdisc не доказывает фактическую дисциплину очереди каждого интерфейса.
Диагностика не измеряет скорость, не проверяет внешний VPN и не включает BBR.

План A/B-теста, без одновременной смены всех параметров:

1. Одно устройство, одна сеть, один аккаунт, одинаковые файлы. Отдельно Wi-Fi и
   мобильная сеть. Сравнить загрузку ленты/Reels и отправку собственного видео.
   Для каждого режима сделать 3–5 повторов; учитывать кеш и сравнивать медианы,
   ошибки и буферизацию. Не публиковать тестовые ролики.
2. Проверить потери/RTT телефон→VPS, нагрузку и маршрут VPS→Meta. Убедиться,
   что DNS/CDN Meta следуют proxy-маршруту. Одна скорость Speedtest не равна скорости Instagram.
3. Сравнить QUIC/UDP 443 с TCP только для Meta. Meta использует QUIC, но внешняя
   TCP-обёртка WebSocket может ограничивать его преимущества. Не блокировать UDP
   глобально — это влияет на звонки и другие приложения.
4. Проверить BBR/fq/MTU и Mux. Не менять MTU произвольно, не устанавливать новое
   ядро и не включать tuning-пакеты без исходных измерений и плана отката.
5. При подтверждённой транспортной проблеме добавить отдельный тестовый inbound
   XHTTP либо REALITY/Vision, если его поддерживает клиент. Не заменять действующий
   WS/TLS, не менять рабочие ключи. Рекомендация Xray перейти с WS на XHTTP связана
   с признаками трафика и сама по себе не гарантирует ускорения.

В этой версии новые inbounds и sysctl-настройки не активируются.

## YouTube: эксперимент с выходом, не обещание DNS-блокировки

BlancVPN в FAQ заявляет просмотр без рекламы с российской локацией; Google
пишет о приостановке показа Google Ads пользователям в России. Регион выходного
IP — обоснованная гипотеза. Их отдельный маршрут для YouTube независимо от
выбранной локации остаётся **неподтверждённым предположением**.

DNS-фильтр не умеет надёжно отличать рекламные вставки от видео на тех же доменах.
Не блокировать googlevideo.com и не делать TLS MITM ради этого.

План: отдельный собственный/разрешённый выход для всего YouTube, остальные
сервисы — через нынешний VPS. Сначала сравнить одни ролики, аккаунт, приложение,
регион, скорость и ошибки на нескольких сеансах. Учитывать ограничения российских
выходов. Не обещать постоянное отсутствие рекламы: геолокация и правила Google
могут меняться. Встроенные автором рекламные интеграции остаются частью видео.

Подготовлен отдельный клиентский профиль `youtube-direct-test`: сравнение с
местным выходом устройства. Импорт не активирует его автоматически. Проверка и
возврат к baseline — в [инструкции эксперимента](whitelist-and-youtube-experiments.md).

Дополнительного выходного узла сейчас нет: фиктивный outbound не добавлен, видео
не ломаются из-за несуществующего маршрута. Решение требует отдельного выбора
инфраструктуры и проверки, а не покупки сервера автоматически.

## Проверки и развёртывание

```bash
python3 build.py
python3 build.py --check
bash -n install.sh
python3 -m unittest discover -s tests -v
```

Тесты доменных правил используют явно обозначенную reference-модель, не реальный
Happ и не живые геобазы. CI отдельно проверяет настоящий TLS→WS→VLESS→HTTP и
передачу routing-заголовка через nginx. Клиентские исключения и скорость требуют
проверки на реальных устройствах; TCP-мониторинг для этого недостаточен.

Для действующей 3x-ui после проверки и слияния изменений загрузить сгенерированный
скрипт, сначала запустить `--dry-run`, затем применить его. Для standalone сначала
обновить управляющий скрипт из `python3 build.py --manager`, сохранив старый и
резервную копию состояния, затем `sa-vpn routing` и `sa-vpn doctor`.
Не запускать installer поверх существующей 3x-ui. Применение экспериментального
профиля на сервере допускается только явно с `--profile runetfreedom`;
возврат — `--profile baseline`. Обновление подписки и reconnect нужны после обоих.
